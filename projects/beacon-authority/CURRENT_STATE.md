| Rewind (bp1) | **Yes** | A held certificate whose cutover is below a node's tip orders a rewind: the node writes `data/rewind.dat`, restarts in-process (a fresh server in `main()`), cuts its ledger after the cutover (or joins fresh) before mounting it, and reports it on `STATUS.rewound` — unattended, on beacon, relays and miners (B022, B023), within seven days of slots, deeper on the operator's `--approve-rewind` (B025); a node back online rewinds too — normative in [BEACON_AUTHORITY.md § Rewind](../../docs/contracts/BEACON_AUTHORITY.md#rewind). |
| Certificate v2 (bp2a) | **Yes** | A cutover comes with its block's hash (`cutoverHash`) and commits right after it; it may not drop the block that committed the generation in force; a node holding another block at the cutover halts instead of rewinding; a node behind the cutover syncs to the vouched block with no tip; a node with no blocks is bounded by its upstream's `STATUS` certificate; `mk-beacon-cert --cutover` reads the block from a node and shows the depth; `dialHints` carried (B026) — normative in [BEACON_AUTHORITY.md](../../docs/contracts/BEACON_AUTHORITY.md#later-generations--t_beacon_cert-record-18) |
| Reaching the beacon (bp2b) | **Yes** | Relays (`beacon` / `beacons`) and miners rank their upstreams — configured plus the certificates' `dialHints` — by parallel `STATUS`: the highest generation they could verify, then the longest chain; at start, every minute, on a new certificate, on a failed sync. New certificates go to every upstream; only the upstream followed is "own upstream" ([B027](DECISIONS.md#b027--nodes-rank-their-upstreams-own-upstream-is-the-one-followed)) — normative in [BEACON_AUTHORITY.md § Upstreams](../../docs/contracts/BEACON_AUTHORITY.md#upstreams) |
| Taking over (bp3) | **Yes** | `pp-beacon --promote` turns a relay's directory into the beacon taking over (checked first: no signed tip, a held certificate with a cutover naming its key, block *C* as vouched, the clock against the network); it commits only block *C*+1, which the slot leader fills with the certificate, charges no outage, and signs from there; relays and miners recalibrate on a new generation (ms offsets); case 2 end to end in `--suite takeover` ([B028](DECISIONS.md#b028--the-leader-carries-the-takeover-certificate-a-cutover-certificate-has-no-window)) — normative in [BEACON_AUTHORITY.md § Taking over](../../docs/contracts/BEACON_AUTHORITY.md#taking-over). |
| Moving the server (bp4) | **Yes** | Case 3 is plain operations: the runbook [MOVING_THE_BEACON.md](../../docs/ops/MOVING_THE_BEACON.md) (whole work directory after a clean stop — key, identity, ledger, signed tip; relays list the new address as a second candidate; retire the old host first; never both); `--suite move` drills it (same peer id on another port, the relay follows within a minute or two, same generation, no rewind). A beacon with no `data/signed-tip.dat` does not sign a ledger past genesis unless `--accept-ledger-tip` ([B029](DECISIONS.md#b029--a-beacon-with-no-signed-tip-does-not-sign-a-ledger-past-genesis-unasked)). |

Nodes verify the beacon end to end: every block they commit lies below a signed tip whose key
the admin-signed trail from genesis certifies, through any number of relays. Part 2 so far: rewind (bp1),
certificate v2 (bp2a), reaching the beacon (bp2b), taking over (bp3), moving the server (bp4).
Case 1, re-genesis, is designed (bp5); bp6–bp10 build it.
